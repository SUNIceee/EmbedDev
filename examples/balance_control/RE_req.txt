Three-loop Balance Control — project-derived bounded C application task

Provenance and scope: adapted from example/1control/control requirements/API. This task covers acquisition, three control loops, decimation/interpolation, output fusion, and logical motor commands. It is not a complete STM32 firmware or a new open-source project. The shared device callbacks replace missing HAL and sensor libraries. Do not provide main or implement platform callbacks.

BC-R01 Reset: control_init() sets all public sensor/output globals to zero and all private loop state to zero: velocity error history e1/e2, int32 accumulator, old/new interpolation endpoints and counter; direction filtered-history value, old/new endpoints and counter. It performs no platform callbacks. All other API calls require control_init first. Reinitialization has identical effects.
BC-R02 Parameters and arithmetic: use the constants in the shared public declarations unchanged, float arithmetic for PID/filter expressions, and int32_t persistent velocity accumulator. Conversion float to integer truncates toward zero. Integer interpolation divides only after multiplication, also truncating toward zero. Input assumptions and ranges are in the device contract.
BC-R03 IMU acquisition: get_mpu() calls board_read_imu exactly once and refreshes pitch/roll/yaw and gyrox/gyroy/gyroz from that observation. It does not advance a control-loop counter or drive a motor.
BC-R04 Encoder acquisition: get_speed() reads channel 0 then channel 1, clears channel 0 then channel 1 exactly once each, and returns (abs(left_count)+abs(right_count))/2 using non-overflowing arithmetic. Count -32768 is valid. It does not itself assign the public speed global; get_pwm performs that assignment.
BC-R05 Angle loop: angle_proc() returns -(int32_t)(550.0f*(0.0f-pitch)-2.0f*(float)gyroy). It has no integral/history state, no callbacks, and does not alter public sensor variables.
BC-R06 Velocity update recurrence: an actual PID update uses e=0.0f-(float)measured_speed, P=8.0f*(e-e1), I=0.1f*e, D=0.5f*(e-2.0f*e1+e2). If I>10.0f or I< -10.0f, replace I by 0; I exactly +10 or -10 is retained. Compute the updated accumulator from the float expression ((float)accumulator+P+I+D), truncate toward zero to int32, then clamp the accumulator itself to [-4500,4500]. Finally set e2=e1 and e1=e. The clamped accumulator is the new velocity endpoint. Do not retain an unclamped hidden accumulator.
BC-R07 Velocity schedule: velocity_proc owns a counter initially 0 and old/new endpoints initially 0. At entry, if count>=5, first reset count to 0, old=new, then update PID and new. Always increment count once before returning old+(new-old)*count/5. Thus calls 1..5 after reset return 0 and the first PID update occurs on call 6; following updates occur on calls 11,16,... . The measured_speed of the update call is used; samples on other calls do not update PID history.
BC-R08 Direction filtering: every direction_proc call, including a non-update call, computes filtered=(int16_t)(0.9f*(float)gyroz+0.1f*(float)previous_filtered), stores it in both public gyroz and the private previous_filtered. The history is the previous filtered value, not the previous raw sample. A caller that wants a fresh sample invokes get_mpu before direction_proc, as get_pwm does.
BC-R09 Direction update: when its own independent counter is at least 5 at entry, read board_direction_error exactly once into public state. Dynamic P is always enabled in this profile: Pgain=clamp(0.6f*(float)measured_speed,50.0f,500.0f). Compute Pterm=(int32_t)(Pgain*(float)state/25.0f) and Dterm=(int32_t)(1.5f*(float)gyroz/100.0f) separately, then clamp Pterm+Dterm to [-3000,3000] as the new direction endpoint. No direction-error read occurs on non-update calls.
BC-R10 Direction schedule: use its own count and endpoints, all initially zero. Filter first; then if count>=5 reset count=0, old=new and update the new endpoint using BC-R09; finally increment count and return old+(new-old)*count/5. First update is call 6, then 11,16,... . Velocity calls do not advance direction state and vice versa.
BC-R11 Fusion: get_pwm() performs get_mpu acquisition, get_speed acquisition and assignment to public speed, then one angle calculation, one velocity step and one direction step, in that order. Store these three results in ac_pwm/vc_pwm/dc_pwm. Set left_pwm=ac_pwm-vc_pwm+dc_pwm and right_pwm=ac_pwm-vc_pwm-dc_pwm. Use the current acquisitions, not stale global values. This API computes outputs but does not write a motor; caller separately invokes motor_proc(left_pwm,right_pwm).
BC-R12 Motor argument isolation: motor_proc(left,right) uses its passed arguments, independently clamped to [-7200,7200]. It does not read stale left_pwm/right_pwm to choose duty, does not change public output globals, and performs exactly one board_motor_write for channel 0 followed by one for channel 1. Full int32 argument range, including INT32_MIN, is accepted by clamping before taking magnitude.
BC-R13 Motor polarity: for a clamped argument >=0, write in_a=false, in_b=true and duty=argument; for a negative argument, write in_a=true, in_b=false and duty=-argument. For zero, forward polarity with zero duty is required. channel 0 maps to PC6/PC7 + TIM3 CH1; channel 1 maps to PC8/PC9 + TIM3 CH2. Never write both direction bits high or a duty above 7200.
BC-R14 State and side-effect ownership: only get_mpu refreshes IMU values; direction_proc may additionally filter gyroz and refresh state at its update. Only get_pwm assigns public speed and ac_pwm/vc_pwm/dc_pwm/left_pwm/right_pwm except control_init reset. Neither direct angle/velocity/direction calls nor motor_proc should overwrite these public output snapshots. Only motor_proc emits board_motor_write calls. All entry points return without waits or retry loops.
